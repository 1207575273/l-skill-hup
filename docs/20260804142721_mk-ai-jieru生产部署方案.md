### 1.4 两个必须先解决的阻塞项

**阻塞一:服务器拿不到代码。**

服务器 `~/.ssh/` 下**只有 `authorized_keys`,没有任何私钥**,而公司 Git 服务只开了 SSH:

```
192.168.160.65  端口 80/443/8929/8081 全部关闭,只有 2222 开
```

所以 `git clone` 现在必然失败。解法见 2.1,**需要一次人工动作**。

**阻塞二:prod 档目前起不来 —— 缺两个必填环境变量。**

`application-prod.yml` 要求这两个变量,而 `docker/docker-compose.yml` 的 `app-prod` 与
`docker/.env.example` 里**一个都没有**(实测 `grep -c` 均为 0):

| 变量 | 缺失后果 |
| --- | --- |
| `BOOTSTRAP_ADMIN_PASSWORD` | `BootstrapAdminEnvironmentValidator` 在 `EnvironmentPostProcessor` 阶段直接拒绝启动 |
| `INSTALL_PUBLIC_BASE_URL` | 占位符解析不出来,启动失败 |

这说明 **prod 档从来没有被真正跑起来过** —— dev 档两个变量都有默认值,所以一直没暴露。

第一条是刻意设计的响亮失败(3.2:"一个带公开默认密码的 ADMIN 比没有管理员更危险"),
不该给默认值;要做的是**在 compose 里把它透传下去,并写进 `.env.example` 做说明**。

## 二、部署方案

### 2.1 让服务器能拉代码(需要你操作一次)

在服务器上生成一把**专用于拉取的部署密钥**,把公钥加到 Git 服务的仓库 Deploy Key 里。

**为什么不是把本机的 `landray_rsa` 拷上去**:那是你的个人密钥,权限覆盖你所有仓库,而这台机器是
多人共用的(上面还跑着 Langfuse 和 Nacos)。部署密钥可以设成只读、只对这一个仓库有效,丢了也只丢这一个仓库的读权限。

**为什么不用 ssh agent 转发**:一次性部署可以,但之后每次更新都要求操作者本机带着 agent,
而部署应该是"登上服务器就能做完"的事,不该依赖某个人的终端状态。

服务器侧(我来执行):

```bash
ssh-keygen -t ed25519 -N '' -C 'skill-hub-deploy@landray-model' -f ~/.ssh/skillhub_deploy
cat ~/.ssh/skillhub_deploy.pub
```

然后**你把输出的公钥**贴到 `192.168.160.65` 上 `yangs1/l-skill-hub` 仓库的
Deploy Keys(只读即可,不要勾写权限)。

加完之后服务器侧配置 SSH 别名并验证:

```bash
cat >> ~/.ssh/config <<'EOF'
Host company-git
  HostName 192.168.160.65
  Port 2222
  User git
  IdentityFile ~/.ssh/skillhub_deploy
  IdentitiesOnly yes
EOF
chmod 600 ~/.ssh/config
git clone ssh://company-git/yangs1/l-skill-hup.git /home/admin/skill-hub
```

### 2.2 补上 prod 缺的两个环境变量

改两个文件,这是代码变更,走正常提交推送流程,不在服务器上手改。

`docker/docker-compose.yml` 的 `app-prod` 环境块补:

```yaml
      BOOTSTRAP_ADMIN_LOGIN: ${BOOTSTRAP_ADMIN_LOGIN:-admin}
      BOOTSTRAP_ADMIN_PASSWORD: ${BOOTSTRAP_ADMIN_PASSWORD}
      INSTALL_PUBLIC_BASE_URL: ${INSTALL_PUBLIC_BASE_URL}
      LOCAL_REGISTER_ENABLED: ${LOCAL_REGISTER_ENABLED:-false}
```

`BOOTSTRAP_ADMIN_PASSWORD` 与 `INSTALL_PUBLIC_BASE_URL` **刻意不给 `:-默认值`** —— 没配时
compose 会把它传成空串,让应用在启动最早期响亮地失败,而不是带着一个猜出来的值跑起来。

`docker/.env.example` 同步补上说明。

### 2.3 服务器上的 `.env`

`docker/.env` 已被 `.gitignore` 忽略,**在服务器上现写,不进仓库**:

```bash
cd /home/admin/skill-hub
cp docker/.env.example docker/.env
```

必须改的四项:

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `DB_PASSWORD` | 随机强口令 | 用 `openssl rand -base64 24` 生成 |
| `BOOTSTRAP_ADMIN_PASSWORD` | 随机强口令 | 首个管理员,登录后立刻改掉 |
| `INSTALL_PUBLIC_BASE_URL` | `http://192.168.160.49:18080/skillhub` | **必须带 context-path**,安装脚本里的下载 URL 与一键安装命令都从它拼 |
| `LOCAL_REGISTER_ENABLED` | **`true`** | 本次部署明确要开自助注册,见下方"三、2" |

`docker/.env` 落盘后 `chmod 600`,里面有两个明文口令。

### 2.4 起服务

```bash
cd /home/admin/skill-hub
docker compose -f docker/docker-compose.yml --profile prod up -d --build
```

三阶段构建(node 打前端 -> maven 打 jar -> jre 运行),首次约 5~10 分钟,取决于依赖下载。
本机与服务器**都没有 buildx**,走经典构建器,而 `docker/Dockerfile` 本来就是按这个约束写的
(根 CLAUDE.md 8.6),不需要改。

### 2.5 验收(每条都要真跑,不看启动成功就算数)

```bash
# 1. 容器都健康
docker compose -f docker/docker-compose.yml --profile prod ps

# 2. 健康检查真的 UP(首页是静态文件,DB 挂了也 200,探不出问题)
curl -s http://127.0.0.1:18080/skillhub/actuator/health

# 3. Flyway 真的建了表 —— 8.2 踩过的坑:迁移不执行且不报任何错
docker exec skillhub-postgres psql -U skillhub -d skillhub -c '\dt'

# 4. 从别的机器访问(ufw inactive,应该直接通)
curl -sI http://192.168.160.49:18080/skillhub/

# 5. 引导管理员能登录
curl -s -X POST http://192.168.160.49:18080/skillhub/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"admin","password":"<刚设的口令>"}'

# 6. 日志是合法 JSONL
docker exec skillhub-app-prod sh -c 'tail -1 /app/logs/skill-hub.jsonl'
```

第 3 条是硬性的:根 CLAUDE.md 8.2 记过一次"应用正常启动、健康检查 UP、库里一张表都没有"的事故,
**任何基础设施接进来都要有一个能证明它真的跑了的验证动作**。

## 三、几个刻意的取舍

**不装 Nginx。** 前端产物已经打进 jar 同源托管(项目宪法第二节)。内网直接暴露 18080 即可,
加一层反代只是多一处要维护的配置。将来真要域名 / HTTPS 再说。

**`LOCAL_REGISTER_ENABLED` 开到 true —— 这是本次部署的一个明确决定,不是默认值。**

代码里的默认仍是 `false`,`.env.example` 里也仍是 `false`。开是在服务器的 `docker/.env` 里开的,
所以它天然是"某个人在某台机器上做的一次决定",而不是一个悄悄生效的全局默认。这正是
`application-prod.yml` 那段注释想要的形态。

**开之前应该知道的**:内网谁都能访问页面,开着意味着任何人都能注册 -> 上传结构合规但正文恶意的
skill -> 被别人装进 Claude Code 执行。这个平台分发的是**会被 Agent 执行的内容**,而认证机制覆盖的是
"有没有人看过",不是内容语义 —— 没有任何一道自动防线能判断一段 prompt 是不是恶意的。

**开了之后仍然成立的**(不要因为开了注册就以为其余防线也没了):

- 上传必须登录,`skill.owner_user_id` 记的是真实账号,出事能追到人
- 服务端完整重做一遍包校验(前端那份只为即时反馈),zip-slip、zip 炸弹、解包上限一条不少
- ADMIN 随时能 `POST /users/{id}/disable` 禁用账号并踢下线
- ADMIN 能撤销版本认证,撤销后新生成的安装脚本默认中止

**残余风险**:注册没有任何审批与域限制,内网可达的人都能开号。真出问题时的处置是事后的
(禁用账号 + 撤销认证 + 下架),不是事前的。要收紧的话,下一步是接钉钉登录(P1,`user_identity`
表结构已经建全,接上时零迁移),用组织身份替代自助注册。

**PG 只绑 `127.0.0.1:15432`。** 数据库不对外暴露,只给本机与本机容器网络用。同机 Langfuse 的 PG
也是这么做的,一致。

**用命名卷,不用绑定挂载。** 与本地开发的约束一致(根 CLAUDE.md 10.1)。`down` 不删数据,
`down -v` 会删。现阶段库里是 skill 制品与元数据,真删了让大家重新上传即可,不值得为此加部署复杂度。

**容器内时区 Asia/Shanghai,宿主是 UTC。** Dockerfile 里已经设了 `TZ=Asia/Shanghai`,所以
`docker logs` 与 JSONL 里的时间是东八区;但 `docker ps` 的 `CREATED`、宿主 `dmesg` 之类仍是 UTC。
排查时两边对时间要留意差 8 小时,**不改宿主时区**——那台机器上还有别的服务在跑,改它影响面不可控。

## 四、更新流程(以后每次发版)

```bash
cd /home/admin/skill-hub
git pull
docker compose -f docker/docker-compose.yml --profile prod up -d --build
```

`--build` 会重新构建镜像;依赖清单没变时 maven / npm 那两层命中缓存,通常 1~2 分钟。

**停服务必须带 `--profile`**:

```bash
docker compose -f docker/docker-compose.yml --profile prod down
```

不带时 compose 看不见带 profile 的服务,`down` 会静默地什么都没停,而命令本身返回 0
(根 CLAUDE.md 第十节)。
